# 量化信号与成交的跨页时间排序修复

## 原因与复现

原实现先请求后端的一页记录，再在该页内执行排序。后端量化信号和成交接口没有 `sort_by` / `sort_order` 参数，第一批记录按接口原有顺序返回，前端倒序无法把后续页中的最新记录移动到首页。

2026-09-06 对真实接口核对：2026-09-04 有 171 条信号和 170 条成交。按每页 50 条请求，第一页基本为 09:39 的记录，最新记录实际为 13:36，代码 603195。

## 修改

- 信号和成交按当前筛选条件取齐记录，统一排序后再按用户选择的每页条数分页。每次后端请求最多 200 条，兼容接口返回的较小分页大小。
- 后续请求沿用第一页解析出的交易日期和筛选条件，避免请求「最新」时跨日期混合。检查页码、每页条数、交易日、策略、总数与记录数量；加载失败或分页不完整时不展示部分记录作为完整排序结果。
- 翻页、切换排序、改变每页条数使用已经加载的完整结果，不重复请求接口。切换排序回到第一页；刷新后页码超出新范围时回到有效页。
- 信号时间与成交时间各自使用实际时间戳比较，兼容时区偏移；无时区的行情时间按上海时间解释。空时间、非法时间始终排到最后，相同时间保持稳定顺序。
- 页面显示当前排序字段、「最新在前 / 最早在前」和返回数据的交易日期。
- 保留筛选草稿、策略间状态记忆、快照版本刷新、请求取消、旧响应隔离和撮合详情。

接口尚不支持服务端排序，因此初次加载成本随当前筛选记录数增长；翻页不产生额外数据请求。本次真实数据各用一个 200 条上限的请求即可取齐。观察池和持仓的分页方式未在本次变更范围内调整。

## 验证

- 全量 43 个测试文件、250 项测试通过，生产构建和量化 TypeScript 检查通过。
- 使用 205 条跨两个后端页的测试数据，验证信号、成交均在全部记录排序后分页，遍历显示页无遗漏或重复，切换排序及每页条数回到首页。
- 测试时间字段切换、不同 UTC 偏移、跨日、同刻稳定顺序、缺失值、空数据、不完整分页、加载期间总数变化、中断请求及刷新后页数缩减。
- Chromium 连接真实后端，逐页对比 171 条信号及 170 条成交的完整升降序结果；13:36 的记录正确显示在最新排序首页。
- 浏览器时区设置为 America/New_York，仍显示上海时间。检查 390px 手机宽度、每页条数调整和页面无横向溢出；无浏览器运行时异常。
