请在现有股票后端中优化“短线情绪 → 单题材前七只股票全天秒级叠加图”的取数链路，完成实现、测试、性能核验及接口文档更新。先阅读当前源码、docs/短线情绪接口.md、docs/短线情绪OpenAPI.json 和在线 /openapi.json，以实际实现为准。

一、现状与目标

前端已经改成左侧选择题材，右侧只挂载当前题材的大图。成员从全部有效成员中按 intraday_streak 降序、board_run.limit_up_days 降序、change_ratio 降序选择前七，未触板股票也参与。缺失值排在已知值之后，同分按字符串代码稳定排序，不把 target_streak 当成已实现连板。

目前复用 /api/v1/stocks/{code}/snapshots 和 /auctions。真实接口限制单次时间窗口不超过 15 分钟，limit 最大 1000；30 分钟请求已实测返回 422。因此七只股票的全天走势需要上百次 HTTP 请求，响应还包含叠加图不需要的盘口等字段。

2026-10-15 前端开发环境经现有代理测得：旧调度首次完整读取约 46 秒，约 120 次行情请求，单次请求中位耗时约 1.3 秒；不经过图表的单独读取也约 0.9 秒。耗时包含网络和代理，不能直接当作数据库耗时。

前端已做：全局最多四个行情时间片请求、七只股票按时间片轮转、只读当前题材、取消失效请求、历史时段缓存和增量续读、100ms 合并视图通知、事件独立限流。第一轮复测七条曲线约 6.9 秒开始显示，但全天历史约 49 秒，128 次请求、解码正文约 25.9 MB。前后采样截止时刻不同，不作为严格同数据量的性能对照。需要后端减少实际往返次数、重复读取/解压和无用传输，不能只依赖前端增加并发。

固定 2026-10-14 历史消费题材的最终核验：第一批曲线和事件约 5.4 秒出现，七条曲线约 7.0 秒出现，完整读取约 48.1 秒，126 次行情请求，解码正文约 26.7 MB。图表开始显示更早，但全天读取问题仍需要接口层解决。前七变化时，前端现只取消被移出的股票，不再重启仍保留股票的读取。

二、接口需求（下述路径是建议，请结合现有结构确定，并交付最终契约）

1. 新增批量、精简、全天曲线查询，例如 GET /api/v1/sentiment/stock-series：
   - 支持 scope、trade_date、snapshot_id、codes；至少支持一次返回七只股票。trade_date 省略时按最新已发布交易日，以 meta.trade_date 为准。
   - 一次获取 09:30 至 15:00 的真实归档采样，包含午间收盘、14:57 后收盘竞价和 15:00 最终撮合。按查询基准 as_of 截止；不返回未来采样。
   - 新批量接口不能仍要求前端按十五分钟拆分；不要简单在服务端逐个循环调用原 HTTP 接口。
   - 返回 {meta, data}，每只股票至少包含 code、board_type、状态和 points。点保留 observed_at、source_time、price、previous_close，或等价的明确文档化字段；change_ratio 若提供应为小数。除非用于既有有效性规则，不传五档盘口、成交额等无关大字段。可采用有明确字段顺序的紧凑数组。
   - 明确每股 loaded_through、partial/truncated/缺失原因，区分“没有行情”和“尚未加载完成”。单股无数据不伪造价格，也不要使其余六只完全不可用。
   - 事件可以随批量结果附带，或提供对应的批量事件读取方式。保留 event_id、code、type、observed_at、source_time、timing_basis；事件分页与曲线增量使用不同游标，避免混用。

2. 支持增量读取：
   - 初次读取全天，后续只返回新增或明确修订的采样，不能每五秒重发全天七只数据。
   - 明确点的稳定去重键、相同时间不同来源的选取规则、修订的 upsert/replace 语义、分页 has_more/next_cursor 和是否全部完成。
   - 游标作为不透明字符串，隔离 scope、trade_date、股票集合和归档重建版本。正常快照推进不能导致每次强制全量重读；历史重建时应使旧缓存/游标失效并明确通知重新同步。

3. 提供可选的题材前七查询，或在题材叠加图入口直接返回排名与曲线：
   - 避免前端每次为选七只而拉取数百个成员的全部分页。
   - 从全部符合范围和筛选的成员中排序，不能只在触板/涨停名单或第一页中取七个。
   - 排序与前端一致：当前实际连板数 → 多日多板的板数 → 涨幅，均降序；保留 board_run.label 的原意。
   - 返回本次排行使用的 scope、trade_date、snapshot_id、as_of 及筛选口径；至少兼容默认全部成员以及现有 board_type/status/高度筛选。

三、性能实现要求

先测量再定位：分别记录数据库查询、读取压缩批次、解压、有效性筛选、映射/序列化和传输时间。可提供 Server-Timing 或结构化耗时日志，避免只报告整个请求总耗时。

检查现有存储、索引和查询计划，批量读取所需股票与时间范围，按实际存储模型减少同一归档批次的重复读取/解压。复用当日已完成时段的解码或精简曲线缓存，活跃时段增量更新；相同请求合并，设定合理容量、失效与并发上限。全量与增量都检查压缩传输是否生效。若增加派生缓存，必须可从真实归档重建且有版本失效机制，不能重写原始行情或触发行情补采。

四、必须保持的契约与事实边界

- 默认 scope=all_a，兼容 hs_mainboard；支持 sh_mainboard、sz_mainboard、chinext、star、bse，板块归属读取 board_type，兼容 BJ 和创业板 302，代码保持字符串及前导零。
- 市场统计仍按股票去重，不能把题材相加。题材成员关系不代表已确认的上涨原因。
- 保持当前单股秒级图的数据有效性和去重语义：使用真实观察时间、来源时间与逐点昨收；不能用过期主源替代有效备用源，不能把后续涨跌幅倒填到历史点。
- 保留空值、质量异常、时段缺口、截断和历史未完成状态；不合成“每秒一条”，不补齐报价，不制造开板/封板/回封事件。前端连线不代表缺口存在真实采样。
- snapshot_id/event_id/cursor 都不按固定冒号段数解析，不跨范围比较尾部数字。快照冲突/游标超前返回 409；参数或游标范围日期错误返回 422；历史不存在 404；最新入口无可用快照 503。
- 历史 REST 查询不能被最新 SSE 覆盖。保持既有接口兼容及现有 API 前缀、鉴权、代理规则；此次工作不修改量化账本，不补数，不改行情采集周期。

五、验收与交付

使用同一交易日、同一截止时刻、同一组七只股票对比新旧结果：点数、时间、涨幅、质量选择、午间端点、收盘竞价、事件锚点均一致。覆盖未触板股票、五板块、半天/全天、历史、无数据、异常质量、分页截断、增量去重、历史重建、跨范围/日期错误游标和客户端取消。
